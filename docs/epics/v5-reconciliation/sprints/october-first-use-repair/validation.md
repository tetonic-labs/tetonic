## Journey checks

| Step | User intent/action | Required observation |
|---|---|---|
| 1 | Open the empty product; ask what to do | One clear entry; useful orientation without an agent-form detour, pointless file scan or invented coding project |
| 2 | Explore an uncertain noncoding idea and ask a follow-up | Readable discussion, preserved context, no compulsory proposal or fake tasks |
| 3 | Connect the reference frontier provider and create an agent | Models load in-product after connection; no required website/manual ID; grants and drafts survive setup |
| 4 | Ask about repositories outside the selected empty folder | Honest access boundary and a supported folder-attachment action; no whole-machine search or repeated empty scans |
| 5 | Grant a specific test folder and request a bounded useful result | Real permitted tool use and an inspectable output; outside paths stay denied; retry/failure state is honest |
| 6 | Create/select a team with two available workers | Team name, roster and recipient are visible before execution; no fake activity |
| 7 | Give it work that benefits from independent contributions | Input-specific reviewable proposal, valid total allowance, actual parallel contributions and grounded synthesis without manual agent-to-agent relaying |
| 8 | Start another independent effort during step 7 | Both remain understandable and independently progressing within measured capacity |
| 9 | Inspect a long conversation/result and repair a setup issue | Adequate reading/composing room, stable effort/recipient, no lost draft/scroll, compact truthful usage |
| 10 | Encounter a controlled missing-access, timeout or provider failure | Concise reason, retained work, actionable next step and no unsafe replay; raw evidence remains accessible |
| 11 | Archive an abandoned draft and a settled failure; reload and restore | Clear map without losing history/usage; restore does not start work; active/actionable work remains protected |
| 12 | Return and describe what is working, finished and needs judgment | Status readable without opening every conversation; no conflation of plan generation and completed goal |

Include the owner's exact orientation/repository intents and unseen paraphrases. Use at least one noncoding task and one local-file task through the same runtime. Do not require identical wording or a predetermined DAG. A team should be chosen for usefulness; compare a small direct answer to ensure orchestration does not burden simple requests.

## Engineering and interface checks

- Allocation: zero coordination headroom, stale proposal revision, repair failure, repeated Start and repair allowance exhaustion.
- Access/settings: denied path, symlink/traversal boundaries, missing credentials, changed provider disclosure, new versus already-running agent limits and retained saved settings.
- Work lifecycle: concurrent archive/state change, duplicate archive/restore, continuation lineage, pending approvals and unchanged accounting.
- UI: real desktop browser, narrow viewport, both themes, keyboard and reduced motion; verify status contrast, primary-action placement, overflow, text growth and settings return.
- Model quality: record latency, tool relevance, useful output and user corrections separately from deterministic authority tests. If changing model or limits explains improvement, disclose it.
- Run only checks appropriate to changed behavior. Use existing suites and architecture gates; no tests that merely mirror cosmetic CSS.

## Evidence and go/no-go

For each ticket record: revision, configuration, actual check, result, artifacts and unresolved limitations. Record time to the first useful outcome, clicks/detours, unsolicited/unnecessary plans, repetitions/corrections, manual coordination and consumed allowance. Treat 30-second next-action comprehension as an observation target, not a measured fact or automatic quality guarantee.

This is an additional required release gate. Its exit requires useful first-use and two-agent results, comprehensible parallel work, working setup/recovery actions, and archive/restore under the supported profile. The owner must be able to explain what the team did without the developer narrating its internals. Passing the original technical gates alone cannot substitute for this gate.

Document any missing owner/fresh-user review rather than replacing it with the author's walkthrough. This sprint does not close full team restart, recurrence, 48-hour operation, packaging or every frontier-provider acceptance.
